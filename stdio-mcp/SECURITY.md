# Security

## What this protects

The server sits between a language model and a Demos wallet. The model can
call MCP tools; the human holds the wallet. The design goal is:

> A model that can only call this server's tools cannot move value, link an
> identity, or sign a DACS commitment without a human approving that exact
> action, and can never read key material.

### Controls

| Threat | Control |
|---|---|
| Model sends funds on its own (prompt injection, confusion, runaway loop) | Two-step writes. `demos_tx_submit` runs only after the human approves **off the chat**: on a local approval page reached through a single-use 256-bit link delivered out-of-band (desktop notification, terminal, phone webhook), or with a fallback one-time code delivered the same way. Neither link nor code ever appears in a tool result (unit-tested + fuzzed). The page refuses a mismatched Host or Origin, including a `null` Origin (DNS rebinding, cross-site posts), and changes state only on POST, so link previewers cannot approve. |
| Human approves something other than what is shown | The approval card is generated by the server from the typed action, not by the model. It gives the headline (`PAY 2 DEM → github:acme · testnet · total 4 DEM`), names the recipient from on-chain CCI or prints `UNKNOWN RECIPIENT`, and lists fee, cap left, deliverable and deadline. Control characters are stripped and counterparty text sits in a box marked untrusted. |
| Prompt injection through counterparty data | Prepare results return offer free text and storage contents only under `untrusted_counterparty_text` / `untrusted_content`. Verifier details are single-line and truncated. The countersigned agreement returned by `demos_tx_submit` is the full signed document, including counterparty fields such as `additionalTerms`, so treat it as data. The skill forbids following instructions found in any of these. |
| Forged or edited receipts | Receipts are signed by a per-install receipt key over a digest of the whole receipt, and record the approval method. The verifier rejects receipts without an on-chain tx hash, receipts whose from/to/amount differ from the chain, legacy kinds, and edited bodies. The issuer is only `pass` when pinned with `expected_signer`. A daily Merkle root (`demos-mcp receipts root`) can be anchored to make the log tamper-evident. |
| Emergency stop | `~/.demos-mcp/KILL` refuses every prepare and submit while it exists. |
| Model guesses the code | 40-bit code from a CSPRNG; HMAC-stored with a per-process key, constant-time compare; 3 attempts per action, then void; 10 failures lock writes for the process. |
| Approval for a benign action reused for a malicious one | Each approval (page link or code) is bound to `(prepared_id, action digest)`. The digest covers kind, network, RPC, from, to, amount and fee quote. At submit, the signed bytes must match those approved fields before they are transmitted. Approvals are single use. A new prepare voids any older pending action, including under concurrent prepares; only the newest survives. A decision made while channels are still delivering is kept, and a deny voids the action. |
| Overspend | Daily cap (amount + quoted fee) is checked at prepare and reserved at submit under a cross-process lock file. The unused part is released only when it provably never left the process. The ledger is persisted; a corrupt ledger blocks writes. Optional recipient allow-list. |
| Accidental mainnet use | Testnet default. Mainnet needs `DEMOS_NETWORK=mainnet` + `DEMOS_ALLOW_MAINNET=1` + explicit RPC. Testnet writes and faucet requests are refused in this release. |
| Key material in outputs | Keys load only from an encrypted keystore or chmod-600 file named by the operator — never from tool arguments. Mnemonic, derived private key, passphrase and codes are registered with `SecretGuard`; every tool result and error string is scanned and blocked on a match (full secret, 24-char fragments of key hex/base64, any 4-word run of the mnemonic, or key-named JSON fields). SDK console output is redirected to stderr and redacted. Tool error messages pass through the guard; MCP schema errors are written so they do not echo input values. |
| Double spend on broadcast timeout | The server never re-signs or re-broadcasts. An ambiguous broadcast outcome (timeout, transport error, non-200) is reported as `pending` after polling the same hash, never as `failed`. Note: the SDK transport itself may retry the *same* signed transaction on 5xx; that cannot spend twice (same hash and nonce). |
| Displayed action differs from the signed one | The card shows the approved intent (type, sender, recipient, amount) and a maximum fee quote. At submit, the locally signed bytes must match that intent, with a hash-covered fee at or below the quote, before they are transmitted. The node's confirmation must echo the same hash and fee. Any mismatch refuses. |
| Malformed / hostile DACS artifacts | Strict SIG-6 decoding, domain separation, required-signer rules, CD-1 prices, discriminator checks, CF-5 duplicate-member rejection for JSON text; unresolvable keys, missing session context and Demos not-found are `indeterminate`, never `accept`. |
| Forged lines in the out-of-band message | Control characters (newlines, ANSI escapes, bidi overrides) are replaced in every confirmation line, so model-supplied text (memo, URLs, claims) cannot add or overwrite summary lines; memo and job_id are printable ASCII only. |

## Signing happens only after approval, and is checked before it leaves

`*_prepare` builds an unsigned action and quotes the fee from the node's fee
parameters. It signs nothing and sends nothing to the RPC. After the human
approves, `demos_tx_submit` signs **locally**. Every SDK path that hands a
signed transaction to the node goes through `demos.confirm`, and the wallet
intercepts it there. A signed transaction leaves the process only when its
**signed bytes** match the approved action:

- type, sender, recipient and amount must equal what was approved;
- the hash-covered fee (`content.transaction_fee`) must not exceed the
  approved quote;
- the content hash, recomputed with the SDK serializer, must equal the signed
  hash.

The node's confirmation must then echo the same hash, and any separately
reported fee must equal the signed fee.

What a malicious RPC can and cannot do:
- It cannot obtain a signed transaction the human did not approve.
- It cannot get a higher fee signed by serving different fee parameters at
  submit time. The preflight refuses before transmission. Tested in
  `test/unit/prism.test.ts`.
- After the approved transaction reaches it, it can still broadcast that
  transaction, hold it back, or lie about the outcome. Once signed bytes have
  left the process, any failure is reported as `unknown` with the locally
  computed hash, and the cap reservation is **kept**, never released.

## Live runs

Nothing in this repository has been run against a live wallet or node.
`npm run test:integration` runs the read path and the verifier against the node
named in `DEMOS_RPC_URL`; it has not been run for this import. A live testnet
run of the write path was made in the source repository before the import. Its
logs are not carried here, it has not been repeated for this repository, and
testnet writes are refused in this release.

The CI workflow, which ran the typecheck, the unit tests (mocked SDK, no
network) and the build, is not in this repository. The workflow-pin and
workflow-settings unit tests skip without it.

The CF-5 duplicate-member check covers JSON **text** inputs, including escaped
spellings and deep nesting. Inputs that arrive already parsed as objects cannot
be checked for duplicates. The scanner does not enforce an explicit nesting
bound, and it rejects out-of-range numbers only after parsing.

## Onboarding (wallet creation)

- **Where the phrase goes.** The recovery phrase is generated in this process by the Demos
  SDK, with a CSPRNG-backed 128-bit mnemonic. It is registered with the output guard the
  moment it exists. It is shown **only** in the HTTP response of the local approval page,
  under `cache-control: no-store`, `referrer-policy: same-origin` and a strict CSP (not
  `no-referrer`: under it, browsers send `Origin: null` on the page's own posts, which the
  page refuses). It never
  appears in a tool result, a log, `onboard.json` or a receipt. The leak fuzz in
  `test/unit/onboard.test.ts` checks this. JavaScript strings cannot be zeroed, so the
  phrase stays in process memory until garbage collection.
- **Who can act on the page.** Anyone holding the page link who can reach the page can act on
  it; the link is a bearer token, not human authentication. See the threats below on the
  channels that carry the link.
- **Passphrase rules.** The passphrase is typed on the local page, never in the chat. It must
  be at least 10 characters, with no leading or trailing whitespace and no line breaks.
  - If `DEMOS_KEYSTORE_PASSPHRASE` is configured, the page only accepts that same passphrase.
  - By default the passphrase is **remembered** in `~/.demos-mcp/wallet.passphrase`. That file
    is created exclusively (`O_EXCL`, chmod 600), and an existing file or symlink there is
    refused, never followed or replaced. A same-user process can read it (see threat 1).
  - Untick "remember" to keep the passphrase in memory for this session only.
- **How the keystore is written.** The keystore is written to a private temp file, fsynced,
  then published with `link()`. Publishing fails if a wallet already exists, so an existing
  wallet is never replaced and a partial keystore is never visible. The keystore carries the
  public address, so status checks never decrypt it.
- **Interrupted backups are recoverable.** A wallet created by onboarding carries an
  `onboarding` marker inside the keystore itself. It counts as backed up only when an
  acknowledgement is recorded for **that** address. So if the page was lost or expired, the
  server restarted, or it crashed between publishing the keystore and writing its state,
  `demos_onboard_create_wallet` opens a page where the human enters the passphrase and sees
  the phrase once more. Without the passphrase, the phrase is never shown again.
- **No truncated keystores.** The keystore bytes are written in full, fsynced, read back and
  decrypted before they are published. A short or failed write publishes nothing.
- **Expiry and page flow.** The link expires (expiry is re-checked after the request body is
  read). The acknowledgement step gets its own 15-minute window. Wallet creation has no code
  fallback, because the phrase must be shown on a page.
- **Faucet.** The faucet request sends your address to the KyneSys faucet. It is testnet only
  and locally rate-limited to one request per 5 minutes. Faucet text is returned only as
  `untrusted_faucet_text`. In this release faucet requests are refused, so none is sent.

## Limits of the output guard

`SecretGuard` is defence in depth, not a proof. For key bytes (the wallet seed
and the receipt key), detection is derived from the loaded bytes. The guard
blocks any output containing 5 or more consecutive bytes of a key in any of
these forms:

- hex, upper or lower case, at either nibble parity;
- `0x`-prefixed hex;
- hex separated by spaces, colons, commas or dashes;
- base64 or base64url at any byte offset, which covers DER/PKCS8 and PEM
  wrappers;
- decimal byte lists, such as JSON byte arrays and Buffer JSON.

In practice that means fragments of 12 hex characters, 8 base64 characters or
6 byte values. The mnemonic is blocked as any 4 consecutive words in order,
whether separated by spaces, punctuation or numbering, or written with no
separators. String secrets (passphrase, codes, approval tokens) are matched
literally. Every check also runs on a JSON-unescaped view.

Public data passes. The guard never registers the public half of the SDK's
64-byte key, so the wallet's own address, public keys, tx hashes and
signatures go through. Randomized tests check both directions
(`test/unit/guard.test.ts`).

The guard does not catch transforms beyond these: encryption, compression,
reversal, or interleaving with other data. The main protection is that no code
path reads key material into a tool result in the first place.

## What this does NOT protect (read this)

1. **A shell-capable agent running as the same OS user.** Claude Code and
   similar agents can run shell commands as you. Such an agent could, in
   principle, read the keystore and its passphrase (from the MCP config, the OS
   credential store, or `/proc/<pid>/environ`) and sign transactions without
   this server — or read a code from a log file. The confirmation gate controls
   the **MCP tool path**; it is not a sandbox. Mitigations, strongest first:
   - run the server under a **separate OS user** that owns the keystore (the
     agent's user cannot read it), or on another machine;
   - use the `desktop` or `webhook` channel (codes are not written to any file);
     avoid `stderr` in Claude Code, whose MCP logs may be readable;
   - add Claude Code permission `deny` rules for the keystore, passphrase file
     and state directory, and do not auto-allow `demos_tx_submit` (Claude
     Code's permission prompt becomes a second human gate);
   - keep only small testnet balances in an agent-attached wallet.
2. **A compromised machine or SDK.** Anything with code execution as you, or a
   malicious dependency, is out of scope.
3. **A human who approves without reading.** The code confirms intent only if
   the human reads the out-of-band summary.
4. **Webhook confidentiality.** A webhook (e.g. a public ntfy topic) sends the
   approval link and code to a third party. Use a private endpoint. Anyone who
   sees the link (and can reach the page), or who sees the code and can call the
   tools, could approve the pending action within its 5-minute window.
5. **Local files.** The spend ledger, receipt key, receipts log and KILL file
   are local files that a same-user process can edit (see 1). The daily Merkle
   anchor makes after-the-fact log edits detectable; it does not prevent them.
6. **Approval-page reachability.** By default the page listens on `127.0.0.1`.
   A non-loopback bind is refused unless `DEMOS_APPROVAL_PUBLIC_URL` is https,
   because approval links carry a bearer token. Make that address reachable only
   from your own devices, for example over a private tailnet.
7. **Accept-and-pay ordering.** The payment is signed and node-confirmed before
   the agreement is countersigned. If the payment then fails on chain, the
   countersignature is withheld. If the payment outcome is `pending`, the
   countersigned agreement is returned with that status. If the outcome is
   `unknown` (the RPC errored after receiving the signed payment), **no**
   countersignature is produced. Check the payment hash, then accept the offer
   again if appropriate.
8. **Approval links in process arguments and notification history.** The
   desktop channel passes the link and the fallback code as process arguments
   to `notify-send` or `osascript`, and to `xdg-open` or `open`, so other local
   users can briefly see them in `ps`. macOS also keeps notification text in
   Notification Center. Use a single-user machine, or the webhook or tty
   channel.
9. **Execution is serialized.** Only one approved write runs at a time. A
    submit that arrives while another write is executing is refused, and the
    wallet refuses an overlapping signing operation.
10. `demos_identity_proof_payload` signs the SDK's fixed web2/domain proof
   message without a confirmation code. It moves nothing and only becomes
   effective through a confirmed attestation; it is still a signature by your
   key over a claim string you choose.

## Reporting

This is pre-release software. Report vulnerabilities privately to the
maintainers before public disclosure, using GitHub's private vulnerability
reporting: open the Security tab of this repository and choose "Report a
vulnerability". Do not open public issues containing keys, mnemonics, or
confirmation codes.
