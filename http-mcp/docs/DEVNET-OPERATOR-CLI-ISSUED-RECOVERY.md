Retained recovery uses `operator.createBuyerDriver({composition}).resume({idempotencyKey})` for original readback; never resend or re-publish. The examples below describe the earlier v1 CLI only.

# Process-bound CLI recovery of an issued payment — held gap

The source-owned acceptance starts a test application child through the supported operator, composition and app APIs under the same exact TTY approval controller as the runnable example. Its test-only post-wallet observer writes only public operation, job, Agreement and transaction identifiers, then the application process terminates itself with `SIGKILL`. The parent-owned normalized Node2 source remains external and alive.

At that boundary the public buyer receipt is still `payment-handoff`: it contains the exact pre-send intent and no stored payment hash. The independently validating Node2 fixture has one authenticated, signed and applied native transaction, while the approval journal has exactly one matching approved native-payment request. No private handoff token, custody material, OAuth value or request header is exposed.

The acceptance contract then starts the unchanged `scripts/devnet-demo-purchase.mjs --resume=<same-key>` entry point under a fresh Node process and normal TTY approval prompts. A conforming result must reconstruct operator, app, seller, SDK and buyer state from the same private operator directories, reconcile the exact original issued transaction by its retained intent and current readback, and return the original operation, job, Agreement and payment with the independently read purchased deliverable. It must perform no second payment, payment approval, Agreement CREATE or payment-terms signature; the separate wallet-login signature and genuinely remaining seller SettlementEvidence and Deliverable approvals may still occur.

The v1 CLI does not yet satisfy that contract. The first process was observed as `CHILDKILLED/SIGKILL`, and the pre-resume assertions established five CREATEs, one TEST DEM transfer, one authenticated accepted signed native transaction, one matching approved native-payment record and a public receipt with no payment hash. The fresh unchanged CLI recovered and reported the retained hash through an HTTP 200 report request, but six following read-only MCP verifications remained `payment-observed`; the fresh seller exposed no delivery state and the CLI exited without a deliverable. An earlier retained characterization on the identical runtime records the collapsed disposition as `seller agent response is unavailable or unauthenticated`. No second attempt is made here.

The exact seller failure is not observable from this boundary: `createSellerAgentClient.post` currently maps fetch failures, non-success HTTP status, response-signature failure and response-shape failure to the same `SellerUnavailableError`. Before any protected repair, a separately authorized single-run observer should retain only the seller HTTP status, response-authentication-header presence (never its value), bounded public error code and timing. That would distinguish the compatible repair target without exposing capability material or retrying uncertain effects.

This is therefore a precise executable ordinary held gap, not completed recovery. It does not simulate a dropped HTTP response, establish public Node2 execution or consensus finality, or claim full DACS v0.1 acceptance. The initial child is accurately described as a supported API-driven test process; only the recovery child runs the unchanged purchase CLI.
