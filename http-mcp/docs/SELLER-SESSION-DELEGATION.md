# Seller session delegation (private app transport v1)

## Switch: `openBuyerAccess` (off by default)

Delegated sessions are used only when the operator config (`dacs-node2-demo-operator/v1`) contains `"openBuyerAccess": true`. The value must be a JSON boolean; any other value is refused at startup. There is no environment variable for it, so the deploy env contract is unchanged.

- **Off (default, key absent or `false`):** the operator always opens its custody TEST buyer. Purchase admission refuses every other buyer with `buyer_access_closed` (HTTP 409 in the portal): at prepare, before idempotent replay or Listing/funds reads, and at every later approval, Agreement submission, payment, completion and effectful recheck boundary, before expiry, chain reads, wallet requests or history changes. Cached signing requests, the browser Agreement broker and native wallet relay use the same check; the operator's bootstrap relay applies it too, and answers `operator_starting` (HTTP 503, retryable, nothing forwarded) until the capability exists. Both relays serve buyers only, in every access mode: the operator's custody seller wallet reaches the source in-process (`src/devnet-demo/seller-relay.mjs`), so a relay request naming the seller's address is refused with `seller_wallet_in_process` before any read. That in-process relay acts only while one of the seller wallet's own requests runs: each request's authority is revoked when its work settles, and checked again after a relay request's body is read and immediately before each source call. So a relay request whose body is read after the wallet request settled gets `seller_relay_closed` with no source call and no network request: one made later by a timer or promise, one begun inside the request whose body arrives late, and one made by a promise callback queued before the request settled (such a callback runs just before the revocation, but its body is read after it). The only answer such a queued callback can still get is the fixed relay descriptor (`GET`), which reads nothing. A source call that began before the request settled runs to its end, so what can outlast a request is at most a seller read it started; seller writes still need fresh, single-use seller headers. The native source's `bind` and `signature` phases require the wallet's own RPC auth headers (the same sender signature `confirmTx` and `broadcastTx` require). Every header set is fresh and single-use, for all four: its millisecond timestamp must be within two minutes of the source's clock either way (`wallet_auth_stale`), and a set already used, for any phase, is refused (`wallet_auth_replayed`), before any lease or source call. The wallets sign a new set for every request, so this changes nothing they sign. Used sets are remembered per wallet, at most 256 each: a wallet past that forgets its own oldest and is refused anything it stamped at or before it, so a wallet sending many sets only makes its own older sets stale. Wallets share 4,096 remembered sets; when that is full, the wallet holding the most forgets its oldest, and if none holds more than one, a new set is refused (`wallet_auth_busy`) until sets go stale. The operator's custody buyer and seller are remembered apart from that shared memory, so no other wallet can make them stale or busy. The relays answer these refusals with HTTP 409 and a plain message; a wallet whose clock is more than two minutes off is told so, and the embedded wallet shows it as a clock problem. What single use does not cover is described below. A connection lease that expires frees the source connection at the next fence acquisition, and a wallet's explicit release frees it at once, but neither happens under a running confirm or broadcast: the lease then takes no new work and frees the connection when that call ends. The provider, seller agent, content producer, evidence anchor and final wallet approval also enforce access independently. These checks use the current operator setting, so a foreign purchase prepared before access was closed is refused on resume. The operator's seller-policy purchase resolver independently excludes non-custody buyers; before payment, no manual or policy seller approval or seller-paid CREATE is reached through the refused purchase flow. The single exception to "no seller work for any other buyer" is the `closed-access-19-resend` described below. Each seller-client construction still checks the custody buyer and otherwise throws `seller peer authentication buyer differs from operator test custody`. Seller requests are signed with the custody buyer's own key. The seller transport declaration is `buyer-ed25519-complete-body` with no `delegation` field. The seller does not read a `delegation` field in a request envelope (such an envelope is `peer_envelope_invalid`). No `seller-sessions` directory is created and no wallet is asked to sign a delegation.
- **On (`true`):** any linked buyer wallet can buy. The app signs seller requests with a per-purchase session key that the buyer's wallet delegated, as described below. The seller requires the delegation on every request (`peer_delegation_required` otherwise).

The switch is read at startup. If the private session directory already exists, startup and periodic retirement continue with the switch off; delegation creation and use stay disabled. A foreign purchase resumed after access is closed gets `buyer_access_closed` before any new buyer work, including cached requests and payment handoffs. Operator composition requires the constructed capability; native operator operations also refuse when it is missing. The app refuses to mount the native Agreement relay and broker, and the demo artifact anchor refuses every non-Listing write, without that capability; a caller-built object is refused at construction. The non-operator app is unchanged. Other purchases crossing settings retain the existing exact transport-declaration check (`seller_transport_changed`); nothing migrates silently. `operatorEvidence.openBuyerAccess` reports the setting.

Already-issued writes remain eligible for read-only inspection through recovery and `verify_deal`. Before payment, only issued writes whose outcome is still unknown are read; with none, recovery refuses with no chain access. Inspection authenticates retained original signed CREATEs or reports payment observations separately; it never resends, writes operation history, releases a lane or rewrites an unknown outcome. A retained intent is checked against its own signed job before any source read or recovery, and so is a receipt verification: the anchor authorizes the job of the signed transaction it verifies, and a request naming another job or artifact kind is `invalid`, before any cache, binding or receipt read.

**RPC auth headers are not bound to a phase (stated limit).** The wallet signs only `ed25519:<address>:<timestamp>`, so a header set does not say which phase or request it is for. Single use binds it to whichever request uses it first. Only someone who captures a set before it reaches the operator (for example on the way to the same-origin HTTPS relay) can exploit that, and only once, within the set's two minutes: they can spend it on another phase than the wallet meant, for example taking one 30-second signature lease, or making one bind, confirm or broadcast call, as that wallet. They gain no signature: a confirm or broadcast still needs a transaction the wallet signed, and the wallet's own request with that set is then refused as a replay, so nothing it meant to do happens twice. Binding a proof to its phase and request needs a change to what the wallet signs, or a server-issued challenge it signs; that is a planned follow-up and is not part of this change.

**Named exception `closed-access-19-resend`.** The seller has one nonce lane. When a custody-buyer write (or the custody buyer driver's evidence-lane check) finds an earlier job's seller storage CREATE that was accepted but is missing, it still performs the one-time unchanged resend of [DEVNET-FIXED-PRICE-DEMO.md](DEVNET-FIXED-PRICE-DEMO.md), even when that earlier job's buyer is now outside closed access. The resend uses the original signed bytes, so it involves no new transaction signature, approval or nonce, and happens at most once; the seller key signs only two fresh RPC-auth headers for its confirm and broadcast calls. Its fee was approved while access was open. Refusing it would leave the seller lane `indeterminate` and block the custody buyer too, until an operator unfenced the lane by hand. The source reports each resend under its lane lock, just before the one dispatch, with the resent bytes' own signed job, on every path (a custody write, the driver's evidence-lane check or any other recovery). The operator writes one stderr line with public identifiers only, `closed-access-19-resend: job <jobId> tx <hash>: ...`, when that job's buyer is not the custody buyer (paid or not), or says the job's closed access is unknown when the resend happens before the purchase store is attached. This exception is an owner decision: the resend stays, once, unchanged and logged; strict refusal is not built. If a foreign buyer already paid while access was open, seller policy does not auto-approve further writes. Seller-owned recovery may instead request exact manual approval, whose prompt says plainly that the buyer is outside closed access. That treatment of paid foreign buyers is also an owner decision: exact manual approval with the notice stays possible, and policy auto-approval refuses it.

The app generates a fresh Ed25519 session key when a purchase first requests its identity presentation. The linked buyer wallet signs both the existing DACS identity presentation and a separate delegation during that purchase action. These remain separate signing requests; this change does not implement a combined wallet approval. The buyer still signs the Agreement, CREATE authorization, payment approval and completion signatures in its wallet.

This is the plugin's private loopback seller transport, not a DACS Standard artifact or a chain transaction. The delegation authorizes the app to call the seller for one purchase. It does not authorize signing an Agreement, spending DEM or signing a bundle as the buyer.

The delegation is an exact JSON object `{ payload, signature }`. Its payload has exactly these fields:

```json
{
  "version": "1",
  "kind": "seller-session-delegation",
  "buyer": "did:demos:agent:<64 lowercase hex buyer Ed25519 public key>",
  "sessionPublicKey": "<64 lowercase hex session Ed25519 public key>",
  "seller": "did:demos:agent:<64 lowercase hex seller Ed25519 public key>",
  "listingPin": {
    "listingId": "<Listing ID>",
    "version": 1,
    "contentHash": "<64 lowercase hex Listing hash>"
  },
  "jobId": "<canonical DACS job ID>",
  "notBefore": 1791400000000,
  "expiresAt": 1791400600000
}
```

Times are safe nonnegative integer Unix milliseconds; expiry must exceed `notBefore`. The signing bytes are UTF-8 of:

```
dacs-chatgpt-plugin:seller-session-delegation:v1:<SDK canonicalize(payload)>
```

The wallet signs these bytes with Ed25519, without an extra hash. The delegation signature is decoded with the same `decodeSignature` helper that identity presentations use (`src/wallet/demos-signature.mjs`): 128 hex characters in either case after stripping any number of leading `0x` (so the doubled `0x0x` prefix some wallets return is accepted), or 86 base64url characters encoding 64 bytes. The app stores and sends the accepted signature in canonical base64url. Unknown fields, noncanonical pins, malformed DIDs, invalid job IDs and malformed signatures fail closed (`peer_delegation_signature_invalid`). The request signature made by the session key keeps the existing strict encoding.

## Portal check before the wallet signs

The portal (`public/portal/seller-session-delegation.mjs`, used by `portal.js`) checks the delegation the server sends before the wallet signs anything for the Agreement step, including the identity presentation. It refuses, and nothing is signed, unless:

- the message is the v1 prefix followed by the exact canonical JSON (sorted keys, no whitespace, no duplicate or extra fields) and equals the payload the server described;
- `version` is `"1"` and `kind` is `"seller-session-delegation"`;
- `buyer` is the DID of this purchase's wallet, `seller` is this purchase's seller claim, `listingPin` is exactly this purchase's Listing ID, version and content hash, and `jobId` is this purchase's job;
- the session key is 64 lowercase hex and is neither the buyer's nor the seller's key;
- `notBefore < expiresAt`, `notBefore` is at most 5 minutes ahead of the browser clock, `expiresAt` is in the future, and the window is at most 24 hours.

The portal then logs a readable summary (seller, Listing and hash, job, expiry as an ISO date and time) instead of raw JSON. The wallet's own approval screen still shows the exact bytes it signs.

## Request envelope

The request header `x-dacs-seller-peer` is base64url of canonical JSON `{ payload, signature, delegation }`. The existing request payload, body hash, nonce, Agreement hash and request signing domain are unchanged. Its signature is made by the session key, while its `buyer` field remains the wallet DID. Responses remain signed by the seller and bind the exact request, body and status. Delegation is not included in a response envelope.

Before reserving an intent or invoking a seller operation, authentication verifies:

1. The delegation signature under the buyer DID's public key.
2. The request signature under the delegation's session public key, plus the complete request body hash, method and exact route.
3. Exact buyer, seller, Listing pin and job agreement between the request and delegation; the seller and Listing also match the independently configured endpoint.
4. `notBefore <= now`, and the request itself expires within the existing maximum 60 seconds. While the delegation is live (`now < expiresAt`) the request must also expire no later than the delegation. After `expiresAt` the request is admitted only for readback, as described in "Expiry and recovery" below.
5. The proposal draft's parties, job and Listing match, and delegation expiry is at most its deadline.
6. When the seller retains a proposal or Agreement, its buyer, seller, job and Listing match and its deadline bounds delegation expiry. This read-only scope is obtained from seller state, including durable state after restart; HTTP caller input cannot replace it.

The app verifies the wallet signatures before asking the local context provider for seller Vet writes. It checks the derived Agreement's deadline again before returning a signing plan. With the switch on, the operator checks the delegation instead of comparing the buyer with its TEST custody wallet on each seller-client construction.

Session keys are retained separately under the operator's private `seller-sessions` directory: real, process-owned mode-0700 directory and regular mode-0600 files opened without following symlinks. One exclusive record (`dacs-seller-session-key/v2`) is bound to the operation ID, account ID, buyer, seller, Listing and job. The key matches the delegated public key on every load. Only the public payload and wallet signature enter purchase state or HTTP. No buyer wallet key is stored there. Missing, corrupted or substituted keys fail closed; an existing delegation never silently generates a replacement key. Retention permits process restart without another wallet signature or changing replay identity. Key files contain sensitive transport authority and must not enter logs, public evidence or source control. A record that no longer parses is reported only as `seller session key record is unreadable`; the parser's own message is never passed on, because it quotes the text it failed on, which can be inside the key. They are deleted once their purchase no longer needs the seller (see "Session key deletion" below).

The expiry is the identity-request time plus the Listing deadline interval. Purchase approval expiry and payment gating retain their existing rules. SDK Agreement derivation uses a later generation time plus that interval; both app and seller nevertheless verify the actual Agreement deadline. There is no clock-skew grace or automatic renewal. An expired request or delegation produces an uncertain timeout, never proof that a prior effect was refused.

## Expiry and recovery

A paid purchase must stay recoverable after its delegation expires. So expiry stops new seller effects, not readback of effects the seller already journaled for that job.

After `expiresAt`, every other check above still applies unchanged: the delegation's wallet signature; the session key's signature on the request; exact job, seller, Listing and buyer; the buyer equal to the retained proposal or Agreement buyer; the deadline bound; the 60-second request lifetime; and the nonce replay store. The seller's intent store then admits the request only if it is one of these:

| Route | Kind | After expiry |
| --- | --- | --- |
| `/dacs/v1/agreements/state` | status read | answered |
| `/dacs/v1/bundles/buyer-copy` | read (the store already treats it as read-only) | answered |
| `/dacs/v1/agreements/proposals` | new effect: proposal admission and seller contribution | only the exact journaled request |
| `/dacs/v1/commitments` | new effect: FinalityCommitmentRecord write | only the exact journaled request |
| `/dacs/v1/payments` | new effect: SettlementEvidence and Deliverable writes | only the exact journaled request |
| `/dacs/v1/bundles/request` | new effect: bundle session | only the exact journaled request |
| `/dacs/v1/bundles/countersignature` | new effect: seller copy anchor | only the exact journaled request |

"The exact journaled request" means an intent row already exists for the same effect identity: job, buyer, seller, Listing, Agreement hash, method, path and body hash. If that effect completed, the seller returns its journaled answer. If it is pending or uncertain, the seller runs only its existing read-only reconciliation (`reconcileTransport`) and otherwise answers `operation_uncertain`; it never runs the route again. A replay of an earlier nonce gets its recorded answer, as before. Anything else, including the first request for a job and a payment for a different transaction, is refused with `peer_delegation_expired` (HTTP 408) inside the store's transaction, before any nonce, job, slot, transaction claim or intent is recorded and before the seller agent is called.

The app keeps signing requests with the session key after expiry (the delegation's `notBefore`, scope and deadline are still checked), so its normal recheck can read back a payment the seller already journaled, for example after a lost response. The app's own gates (see "Safety margin" below) keep it from starting new seller writes near or after expiry.

Residual case: if the buyer paid but the seller never journaled the payment submission before the delegation expired, that submission is a new effect and stays held. The pre-payment gate makes this unlikely by refusing to hand over a payment unless the delegation has its safety margin left. There is no renewal; adding a wallet-signed renewal is an owner decision.

The intent/replay store, nonce scope, effect identity, payment reservation and retained uncertain outcomes are unchanged. A lost response never releases an intent or allows another broadcast. Re-entry may return a cached answer or use the existing authenticated readback reconciliation; it cannot invoke an uncertain effect again.

With the switch on, the built-in operator requires delegation even when its optional TEST buyer is present. Legacy injected fixture transports can retain direct buyer-key authentication by leaving delegation unconfigured. Existing purchases prepared with the other transport declaration are held by the existing exact-declaration check; there is no silent migration or custody fallback.

With the switch on, TEST buyer custody opens only for an explicit `buyerFeeBudget` or the command-line buyer driver's `buyerDriver: true` argument, so seller-only hosting does not open the buyer custody record. With the switch off it always opens, as before. Manual seller `APPROVE`, exact debit budgets and all chain-write journals remain unchanged.

## Safety margin

The app starts a step that leads to a new seller write only while the delegation has at least `SELLER_DELEGATION_SAFETY_MARGIN_MS` (5 minutes, `src/dacs/protocol-purchases.mjs`) left. That is longer than one full authenticated seller request (4 minutes). Otherwise it refuses with `seller_delegation_expiring` (HTTP 409); nothing is signed or sent, and the buyer prepares a new purchase.

| Gate | Where | Seller writes it would lead to |
| --- | --- | --- |
| Agreement plan | `planRequest`, right after the delegation is accepted and before the Agreement context read (which can already make seller Vet writes); again in `savePlan` after that read | Vet records, proposal, commit, payment evidence |
| First Agreement signature | `submitAgreementCore`, when no signature is retained yet | proposal and contribution, then the buyer's Agreement CREATE and the seller commit |
| Before payment | `recheckCommitment`, which runs before the approval challenge, the handoff, a handoff reissue and the native wallet guard read | payment evidence and Deliverable |

No gate applies to work already started: a resubmitted signature, the seller commit after the buyer's Agreement CREATE, or the payment submission after the buyer paid. Refusing those would strand what the buyer already spent. The seller still decides each one, and after expiry it answers only from its journal (see "Expiry and recovery").

The 24-hour maximum is enforced by the shared `public/portal/seller-session-limits.mjs` checker at operator config validation, key issuance, delegation acceptance and seller verification, as well as in the portal and headless buyer before signing. Exactly 24 hours is allowed; longer windows fail closed.

## Session key deletion

The operator deletes a purchase's session private key once that purchase can no longer need the seller, and never while it may (`src/devnet-demo/operator-sessions.mjs`, `sellerSessionKeyRetirement`). The operator sweeps the `seller-sessions` directory when its seller agent attaches (so a restart catches up) and then every 5 minutes. It reads each purchase from the app's purchase store by its retained operation and account ID. The operation store persists `state.protocol.sellerSessionFinalAt` on the first transition to a final state. Unchanged observations, final readbacks and signer activity do not move it, and a restart preserves it. Returning to unresolved seller work clears it; reaching final again starts a new grace window. Older records without that field use their last durable change as a conservative fallback; their original final time cannot be recovered from the current row alone.

| Purchase | Key deleted |
| --- | --- |
| `expired`, `terms_changed`, `superseded`, `agreement_rejected`, `payment_failed`, `payment_mismatch` | 15 minutes (`SELLER_SESSION_KEY_GRACE_MS`) after the purchase first became final |
| `settled_verified` at stage `delivered`, or at `delivery-ready` with no delivery evidence pending or held (`delivery.evidenceHold` absent; the end state when delivery evidence is off), with a structurally valid verified delivery and a retained signed payment projection (see below) | 15 minutes after the purchase first became final; successful rechecks do not restart the window |
| `agreement_pending` or `awaiting_approval` whose approval window elapsed (abandoned, even if never marked `expired`) | 15 minutes after the window elapsed |
| `cancelled` | 15 minutes after the delegation expired. Until then a late landing of the old payload can still be recorded and claimed with the key; after expiry the seller refuses a new claim anyway |
| `approved` | never: the purchase is not final (cancelling it ends it) |
| `payment_handoff`, `broadcast_reported`, `payment_uncertain` | never: the payment outcome is unresolved |
| `settled_verified` at any other stage (`payment-observed`, `native-payment-evidence-held`, `payment-evidenced`, `delivery-rejected`), or at `delivery-ready` while delivery evidence is pending or held (`delivery.evidenceHold`) | never: the seller claim, payment evidence, delivery or delivery evidence is not final, so readback may still be needed after expiry |
| `settled_verified` at a final stage whose record lacks a seller-free readback: no verified delivery of that stage, a non-canonical Deliverable reference or hash, no fulfilment or receipt, no settlement pointer, a retained answer that differs from the delivery, or no session delegation (`final purchase record is malformed`) | never: kept and reported |
| `settled_verified` at a final stage without `sellerAnswer.signedProjection` (rows verified before the answer was retained) | not until a seller-backed recheck retains one (below); reported on every sweep. With `DACS_BUYER_CHAIN_READBACK=on`, when `sellerAnswer` or its `signedProjection` is absent (not present but malformed) and the row passes every check of the next row that needs no projection: as a missing chain pointer below (`final purchase has no retained signed payment projection`), retired exactly at the pointer retention bound and held for the operator if a pointer is missing too. A row that fails one of those checks is never retired (next row). Turning the switch off after it retired a row with no `sellerAnswer` leaves that row without a switch-off readback: the switch-off recheck falls back to a pointer derived from the verified delivery, which has no payment projection, so once the seller wallet journal has moved on the row drops to `native-payment-evidence-held` without its delivery on every recheck while the switch is off. With the switch off throughout, the key is kept and the row recovers when the seller answers |
| `settled_verified` at a final stage whose retained answer would not reproduce the verified purchase: another delivery status (other than `delivery-ready` for a purchase verified `delivered`), delivery evidence hash or Deliverable receipt; a retained Agreement that does not hash to its verified hash, whose reference is not canonical for that hash, or whose job, buyer, seller, Listing, payee, price, rail or payment phase differs from the purchase; payment evidence or answer not at the canonical payment-evidence address; no decodable payment receipt, or one not written by the seller for that evidence; a signed projection for another transaction, whose content does not hash to it, that the payment receipt did not authenticate, or that the seller did not sign (`final purchase's retained seller answer cannot authenticate it`). With `DACS_BUYER_CHAIN_READBACK=on` the same checks, apart from the signed projection's, also apply to an answer without its `signedProjection`, and those on the Agreement, payment evidence and payment receipt to a row with no `sellerAnswer` (`final purchase record is malformed`) | never: kept and reported |
| purchase not found, unreadable or malformed key record, purchase scope differs from the record, purchase store error | never: kept and reported |
| With `DACS_BUYER_CHAIN_READBACK=on` only: `settled_verified` at a final stage that has not kept the signed CREATE bytes of its payment evidence, Deliverable or delivery evidence (`final purchase lacks kept chain pointers`), or whose `sellerAnswer` or `signedProjection` is absent (above) | exactly at the pointer retention bound: 7 days after the delegation expires (`SELLER_SESSION_POINTER_RETENTION_MS`; operator config `sellerSessionPointerRetentionMs`, 0 to 365 days). The 15-minute grace is not added to the bound: it covers a seller request already under way when the purchase became final, and a request uses the key only to sign itself when it starts; the bound is never before the delegation expires, after which the seller answers readback-only. Until then kept and reported on every sweep; at the bound retired and the purchase is held for the operator (below) |

The expiry sweep is the same rule: an expired delegation alone never deletes a key whose purchase is in one of the "never" rows.

**Chain readback pointers (`DACS_BUYER_CHAIN_READBACK=on`).** A seller-free recheck then reads the chain only, so a final purchase also needs the signed CREATE bytes of everything it verified, kept in `state.protocol.chainReadback`. A final purchase that lacks one asks the seller's idempotent payment route for it (answered from the seller's effect cache) at most 10 times, at least a minute apart (`CHAIN_POINTER_ASK_LIMIT`, `CHAIN_POINTER_ASK_INTERVAL_MS`, counted in `state.protocol.chainPointerAsks`); other rechecks read back from the retained answer only. Every recheck keeps the verified delivery and payment evidence unless a fresh read definitely contradicts them (a rejected read); refusals, unavailable or malformed seller answers and indeterminate reads record `chain-readback`/`indeterminate` and change nothing. Once nothing can obtain a missing pointer (the asks are spent, or the key is retired, including at the pointer retention bound), the purchase is held for the operator: `state.protocol.chainReadbackHeld` (`action: chain-readback-pointers-missing`, the missing addresses, time and reason), a `protocol_chain-readback` or `protocol_chain_readback_held` event, and for a key retired at the bound an `operatorAction` on its `seller_session_key_deleted` event. Ops health reports such a purchase as `operator-action-required` until a readback keeps every pointer. Nothing is resent.

While a purchase holds a verified delivery, only a definite contradiction of what it already holds lowers it: a rejected read of signed CREATE bytes it authenticated and kept (or of its retained answer's payment projection, which is bound to the verified payment receipt), or bytes that authenticated on the chain in that read and read back otherwise. A rejection of what the seller offers is the seller's problem and never lowers the purchase: signed CREATE bytes that do not authenticate, or a fresh answer whose Deliverable pointer (address, payload hash, fulfilment, settlement or receipt) or delivery evidence hash is not the verified delivery's. The recheck then reads again from the retained answer, as for a refusal. An exception from a chain read that is not one of the reader's definite verdicts (the SR-2 adapter's `invalid`; in the commitment resume, the SDK's counterparty or plain permanent verdicts) is indeterminate, never a rejection.

**A hold is informational today.** Once the asks are spent or the key is retired, no supported action clears it. The seller is not asked again and there is no operator action that imports a signed CREATE, so the hold would clear only if a later readback already held every pointer, and nothing in this build supplies one then. The purchase keeps its verified result throughout: status, stage, delivery and payment evidence stay, and each recheck still re-reads from the chain whatever it holds pointers for. What the operator can check: the hold itself (`state.protocol.chainReadbackHeld`: the missing logical addresses, time and reason), its `protocol_chain-readback` or `protocol_chain_readback_held` event, the purchase's `seller_session_key_deleted` event, and, on the chain, the seller's storage programs at the missing canonical addresses. Nothing should be resent to clear a hold.

The 15-minute grace window exceeds one authenticated seller request (at most 5 minutes). Once delivery is final and the seller answer is retained, rechecks are readback-only: they neither acquire a session signer nor contact the seller, but re-read the native payment evidence and Deliverable through the usual buyer readback (see "Readback after the purchase ends" below). Signing or looking up a key does not extend retirement, and neither does a successful readback.

To delete a key, the sweep first writes a retired marker `<sha256(operation ID)>.retired.json` (mode 0600, no key material: operation and account ID, session public key, time and reason), then unlinks the key file. Deletion is an ordinary unlink, with no secure-erase guarantee on journaling or SSD storage. Unlinking a file does not guarantee erasure of a key already in memory. The sweep revokes handed-out handles and releases their key references; every sign call also checks the retired marker, including handles from another store instance. The operator records `seller_session_key_deleted` (reason and session public key) in that purchase's history. Per-record lookup, malformed-record, malformed-purchase, retirement-decision and deletion failures are reported on stderr, and the sweep continues to other records. A deletion failure after the marker was written still revokes signing; later sweeps retry only local cleanup.

With `DACS_BUYER_CHAIN_READBACK=on`, every sweep (so also the one at startup) also reconciles the retired markers of earlier passes whose key is gone. The marker and the unlink come before the purchase history, so a crash in between leaves a retired key with no `seller_session_key_deleted` event and no hold. A marker is used only when it is a private regular file exactly as the sweep writes it (`dacs-seller-session-retired/v1`, named after its operation) and names an existing purchase whose delegation is the retired key. For each, the operator writes the deletion event if that key's is missing (with `reconciled: true` and the marker's `retiredAt`), and holds the purchase if it is final and still lacks a pointer. Both writes are idempotent, so a restart changes nothing more. Any other marker is ignored and reported on stderr. With the switch off the sweep is unchanged.

Signing and retirement share an exclusive mode-0600 `<sha256(operation ID)>.lock` file across processes. Signing holds it from the retired-marker check through signature generation; cleanup holds it while reading the current purchase, validating scope and eligibility, writing the marker, revoking handles and unlinking the key. Contention refuses signing with `seller_session_locked` and retains the key for a later sweep. Locks contain the holder's PID for investigation. A lock left by a crashed process also fails closed: no timeout or PID check automatically steals it, since a paused signer may still resume. Remove an orphaned lock only after confirming its holder has stopped; keep the session key and retired marker intact.

After deletion, any use of the key for that purchase (signing a seller request, re-requesting or accepting the delegation) fails with `seller_session_retired`, also after a restart. A missing key without a marker is still treated as lost and fails closed as before; neither case generates a replacement key.

### Readback after the purchase ends

Delivery stays current only while the latest native read authenticates it, for delegated purchases exactly as for custody purchases. When delegated delivery first verifies, the purchase retains the authenticated seller answer that led to it (`sellerAnswer`: public pointers to the payment evidence and Deliverable, settlement ID and public signed projection; no key material). A recheck of a purchase whose delivery is final (`delivered`, or `delivery-ready` with no delivery evidence pending or held) and that retains this answer uses it instead of a seller request, before or after key deletion, and runs the same fresh readback: the Agreement, payment evidence (public projection from the seller wallet journal or the retained answer), Deliverable and, where configured, delivery evidence. Its `nativeEvidence.sellerAnswerSource` (`retained; the seller was not asked`) marks the seller fields as retained, not a new seller reply. Delivery remains current only after that read succeeds. An absent, rejected or unavailable read downgrades it exactly as for a custody purchase, and the purchase is no longer final, so its key is kept again. A later recheck asks the seller while the key exists. If the key was already deleted, `seller_session_retired` falls back to the same readback-only path, so restoring the chain state recovers the exact original delivery without the seller. Without any pointer (no verified delivery and no retained answer), a deleted key records the hold as before.

Payment readback authenticates the original CREATE only with its public signed projection. The retained answer is its one durable source: the seller wallet journal keeps a single `sr2/wallet/` row per wallet lane, which the seller's next CREATE on that lane overwrites (in the operator at the latest the next purchase's payment evidence; in the source-demo test composition already the Deliverable), so the journal reader (`readSignedProjection`) cannot be relied on for an older purchase's payment CREATE. A key is therefore deleted only once the purchase retains `sellerAnswer.signedProjection`.

Purchases verified before `sellerAnswer` was retained (legacy rows) have no such answer. While the key exists, a final recheck of a legacy row asks the seller, as on main, and a verified answer is retained with its projection. The grace window is not restarted: the row's final time is still its last durable change before the upgrade, so its key is normally deleted at the next sweep. Until then the sweep reports the row on stderr on every pass (`final purchase has no retained signed payment projection`). With `openBuyerAccess` off, no seller-backed recheck of a delegated purchase is possible (the custody transport refuses it), so such a row keeps its key until access is turned on again and the buyer rechecks it; there is no time bound, because deleting the key would leave no seller-free readback. Once a legacy row's key is gone (deleted by an earlier version), `seller_session_retired` falls back to a pointer derived from its verified delivery, and that pointer is written with every outcome of the readback, so a failed read does not lose it and later rechecks keep reading. Its recovery then depends on the composition finding the payment CREATE projection: the operator's seller wallet journal still has it until the seller's next CREATE on that wallet lane. Not protected: after that, or in a composition without that journal reader (the source-demo tests), such a row stays held. It never projects the old delivery and never asks the seller.

Retirement also requires the verified delivery the pointer is derived from: the stage's delivery record, canonical Deliverable reference and hash, fulfilment, receipt, settlement ID, a retained answer consistent with them, and the session delegation. A final stage with missing or malformed data keeps the key, and the sweep reports it on stderr (`final purchase record is malformed`).

The retained answer must also reproduce exactly what the buyer verified, because after deletion it is all a readback has. Its delivery status, delivery evidence hash and Deliverable receipt must equal the verified delivery's (a native Deliverable receipt on the fields the readback compares). The one status change accepted is `delivery-ready` in the answer for a purchase verified `delivered`: the seller answered before its delivery evidence published (for example, after a failed evidence intent was resumed), and the buyer's fresh read of the same pointer verified the evidence the answer's evidence hash names. The retained Agreement is the one the readback re-reads with, so it must be the verified one: its bytes hash to `agreement.hash`, its reference is the canonical Agreement address for the job and names that hash, and its terms are the purchase's own (job, Listing, payee, rail, price and parties, by the same check that binds an anchored Agreement to the prepared terms, plus the payment phase). Its payment-evidence address, and the verified payment evidence's, must be the canonical one named by the retained Agreement. Its signed projection must be the transaction named by the verified payment-evidence receipt (written by the seller for that evidence), its content must hash to that transaction, the receipt's proof must name exactly this projection, and the seller's key must have signed it. In the operator the seller wallet journal's copy of the projection takes precedence during readback; these checks make sure the retained copy is the same signed transaction, so it can stand in once the journal has moved on. Anything else keeps the key with `final purchase's retained seller answer cannot authenticate it: <why>`, reported on stderr. With `DACS_BUYER_CHAIN_READBACK=on`, a legacy row waits for the pointer retention bound only if it passes these checks without the projection it lacks: the Agreement, payment evidence and payment receipt are the purchase's own verified records, so they are checked even when there is no answer (a failure is then reported as `final purchase record is malformed: <why>`), and an answer without its projection is checked on everything else. These checks bind the answer to records this purchase already verified; they do not replace the fresh native readback, which still runs on every recheck.

Rechecks of one purchase can overlap, and `save()` writes each recheck's own snapshot (it compares only the status). So that an older recheck cannot drop or replace an answer a newer one retained after the sweep deleted the key, every readback outcome reads the stored `sellerAnswer` in the same database transaction as its write and keeps it. Only a fresh seller answer, one this recheck just received from the seller and that binds to this recheck's own verified payment-evidence receipt and delivery by the checks above, replaces it. A retained answer or a pointer derived from a stale snapshot never replaces a stored answer; a derived pointer is written only where none is stored. A fresh answer that fails the checks is not retained, the stored answer stays, and the recheck's `nativeEvidence.sellerAnswerNotRetained` says why (fixed text). The older outcome itself still lands: a late failed read downgrades the view until the next recheck, which reads back from the retained answer. A readback-only recheck that fails before it builds a new payment summary (for example, while the Agreement cannot be re-read) also marks the seller fields it leaves visible with `sellerAnswerSource`.
