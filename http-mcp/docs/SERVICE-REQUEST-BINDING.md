# Public service request and purchase binding

Showcase 8a implements admission only. Buyer requests are not accepted by any MCP tool, purchase route, seller or Agreement composer yet. Today's fixed report remains the active contract. Items 8 and 9 of the showcase plan call for a deterministic public-text report after that report; a personalized result remains a showcase preview with Verify pending until the audited completion profile exists.

## Request contract implemented here

`src/dacs/service-request.mjs#admitPublicServiceRequest()` accepts exactly:

```json
{"type":"public-data","serviceId":"public-text-report","version":"1","input":"Public demonstration text."}
```

`version` is the string version of this service/request contract, not a DACS artifact discriminator. Only this service/version pair is admitted. The JSDoc `PublicServiceRequest` type includes the literal `type: 'public-data'`, and runtime admission requires it. This is a declaration by the buyer, not a classifier that can establish whether text contains confidential information. The eventual review must explain that the input and output become public and must exclude credentials and customer data.

| Constraint | Inclusive limit / policy | Source and reason |
| --- | --- | --- |
| Input characters | 1–2,000, measured by JavaScript string length | Application bound no larger than a Listing description. For admitted ASCII, UTF-16 code units, code points and characters coincide. DACS-1 §6.3.4 sets description 2,000, title/display name 200 and tags 32; it does not set a buyer-input limit. |
| Raw input UTF-8 bytes | 2,000 | Checked after character length, before scans or serialization. On admitted ASCII this equals the character limit; independent enforcement makes the refusal order explicit. |
| Input alphabet | U+0020–U+007E | Every C0 control and DEL is refused, including TAB/LF/CR. Non-ASCII, bidi, zero-width text and lone surrogates are refused. The existing bridge holds non-ASCII at `src/dacs/demos-sr2-wallet-bridge.mjs#snapshot()`; this slice does not broaden its profile. |
| Canonical request UTF-8 bytes | 3,072 | Application allocation, not a Standard limit. Quotes/backslashes consume two JSON bytes, so some inputs below 2,000 characters exceed this budget. The escaped size is counted before serialization. Leaves room within the current 24 KiB artifact envelope. |
| JSON representation | Plain object (Object.prototype or null), four own enumerable data properties | No proxies (refused before any trap can run), arrays, class/custom prototypes, getters, symbols, hidden properties, prototype keys or extra members. Matches the browser's plain canonical JSON subset at `public/portal/embedded-wallet/sdk-provider.mjs#anchorJson()`. |

Admission snapshots the four primitive strings into a frozen object. It preserves whitespace and punctuation exactly, without trimming, case folding or escaping changes to the input value. Object order is discarded. The returned `canonical` string is JSON in lexical member order `input,serviceId,type,version`, with JSON escaping and no whitespace. For this ASCII string-only shape it equals RFC 8785 JCS and CF-1 NFC is an identity operation (CORE §B.2).

```text
requestHash = lowercase_hex(SHA-256(UTF8(canonical)))
```

The hash covers the entire request, including its public-data type, service id and version; no members are omitted and no signature/domain prefix is added. It is an application content hash, not a signed DACS artifact or the purchase operation's `requestHash` (which hashes the complete purchase-preparation request). Identical text in different jobs can intentionally have the same service request hash. Job, Listing and Agreement bindings below supply the session context.

All refusals throw `ServiceRequestError` with fixed messages that do not echo input. Codes in evaluation order: `service_request_shape`, `service_request_type`, `service_request_service`, `service_request_version`, `service_request_input`, `service_request_character_limit`, `service_request_byte_limit`, `service_request_control`, `service_request_non_ascii`, `service_request_serialization_limit`. Oversized strings fail on `.length` before UTF-8 measurement, regex scans, JSON serialization or hashing. Inputs whose escaped JSON exceeds the canonical budget fail before serialization or hashing. The shape check still inspects the four properties.

**Complete-record sizing remains required before signing.** A small request cannot prove that an arbitrary surrounding Agreement, signatures, identity material and storage wrapper fit. The existing wallet independently measures the full artifact envelope at `public/portal/embedded-wallet/sdk-provider.mjs#devnetAgreementAnchorPlan()` and refuses above 24,576 bytes; the relay has a 64 KiB request cap (`src/portal/wallet-rpc.mjs#createWalletRpcRouter()`). Signing duplicates data in storage edits. The wiring must measure the complete signed envelope (or a conservative bound with fixed signature sizes) and serialized CREATE/relay request before asking for signatures. It must retain those gates at actual write preparation too. Output admission must similarly bound the complete result. The 3 KiB allocation is not a guarantee of complete-record encodability.

**Result feasibility precedes Agreement signatures and payment.** An admitted request could otherwise produce a report or signed storage envelope that cannot be delivered, after the buyer has signed and paid. Before the first Agreement signature, and again before payment submission, the wiring must establish that the result fits: run the deterministic producer on the persisted request, or apply a conservative bound with fixed signature sizes. Measure the complete result, signed storage envelope, Deliverable CREATE and relay request against the limits above. Check every seller write against the seller write limits in the table below. For each exact stored envelope, compute the storage-chunk count as max(1, ceil(storageBytes / chunk size)), charged per started chunk. Add SDK gas and the network and RPC fees to get the complete debit. Check that debit against the configured per-write fee cap `maxWriteTotalOs` (refusal `write-fee-cap`) and the operator's `sellerFeeBudget.maxTotalOs`. Network and RPC fees are not fixed: the wallet reads them from the node's `getNetworkParameters` at signing (`public/portal/embedded-wallet/sdk-provider.mjs#nativeDebit()`). At both check points, compute each write's debit from the admitted current network and RPC fees, or from a conservative bound the operator has authorized; a fee read that fails or is not admitted makes the check unavailable. Example, assuming network = RPC = 1 DEM: one chunk totals 4 DEM and fits the default 4 DEM cap, and two chunks total 5 DEM and refuse with `write-fee-cap`. With network 0 and RPC 1 DEM, two chunks total 4 DEM and pass; with network 2 and RPC 1 DEM, one chunk totals 5 DEM and refuses. Account for the per-job seller write limit and the hourly seller budgets `maxWritesPerHour` and `maxTotalOsPerHour` in a rolling hour. Check remaining write and debit budget for every required seller write, including the Deliverable and delivery SettlementEvidence, counting outstanding and unknown reservations across jobs; completed attempts count for an hour after completion. Use the effective `sellerApproval` settings admitted by `src/devnet-demo/operator-approval.mjs#sellerApprovalSettings()` and the operator budget validated by `src/devnet-demo/operator.mjs#validateConfig()`; defaults are examples, not authority to raise a configured limit. A failed or unavailable check before the first Agreement signature means zero Agreement signatures, broadcasts and payment submissions. A failed or unavailable check before payment means zero payment submissions and no further broadcasts, with the signed Agreement held in an explicit non-payable state for readback only, never resent; its existing anchor and seller commitment are retained. A failed or unavailable check at write preparation follows the recovery rules in the 8f row. Delivery keeps its own write-preparation checks; the preflight does not replace them.

Seller write limits, as the code applies them by default at this commit. A configured value admitted by the cited validators is authoritative.

| --- | --- | --- |

The Standard's Listing limit is 16,384 bytes of canonical unsigned scope, including unknown signed members. It separately requires measuring the native record including signature and wrapper (DACS-1 §6.3.4, Anchoring and size limits). The DACS-4 128 KB delivery cap and Demos mapping's 128 KB are looser than this wallet profile (DACS-4 §9.6.1, DEMOS-MAPPING §A.2); they cannot authorize larger writes here.

## Binding points for subsequent PRs

### 1. Signed Listing: advertise the service before accepting input

Current construction at `src/dacs/listing.mjs#buildListingDraft()` advertises a generic seller-defined output schema, not this service's request schema. `src/dacs/listing.mjs#purchaseSupport()` and `src/dacs/purchase-protocol.mjs#protocolSupport()` check the fixed-price DEM pipeline, not a public request contract. Request purchases must additionally require a verified, pinned Listing that advertises `public-text-report` version 1, its public-only input contract and deterministic output contract. A directory description is not authority: `src/dacs/verification.mjs#verify()` compares directory detail with chain bytes and switches to those bytes.

Use the existing signed `offering.description` to explain the service/public scope; `offering.deliverable.schemaUrl` identifies the **output** schema and `accessModel: 'public'` declares output visibility. Proposal for machine admission: `terms.termsOfServiceUrl` and `terms.termsOfServiceHash` reference the exact versioned application contract containing both request and result schemas, limits and algorithm version. Compare against a locally supported contract hash; do not fetch a schema supplied by an untrusted Listing. Republish a new signed Listing version when that contract changes. Pin its `(listingId, listingVersion, contentHash)` in the purchase.

Spec: DACS-1 §6.3.4 schema, canonical signature, LR-1..LR-3; DACS-4 §9.3 DeliverableSpec/DeliverableRef. **There is no normative Listing `serviceId` or request-schema field in this snapshot.** The terms-of-service reference is an application convention, and output `schemaUrl` is not defined as an input schema.

Question for the Standard: “For a fixed-price service taking buyer input, is a signed `ListingTerms.termsOfServiceUrl`/`termsOfServiceHash` reference an appropriate place to advertise the service/version and request schema, or should DACS define a first-class request-schema contract? How does a reader establish support before accepting that input?”

### 2. Durable idempotency and approved purchase terms

Hook `src/purchases.mjs#prepare()` before side effects: admit the request, check the feature gate and Listing contract, and include the complete admitted request plus its digest in the preparation request built in that function. Store the same immutable request/hash in that function's `terms` so its `termsHash` commits to them. Proposed application fields are `serviceRequest` and `serviceRequestHash`. The existing idempotency key stays scoped to account + kind + key; do not replace it with the service request hash.

Both the fast replay comparison at `src/purchases.mjs#prepare()` and `src/operations.mjs#createIdempotent()` must receive the request-bearing preparation shape. `src/operations.mjs#requestHashOf()` hashes that complete shape. Same key + reordered request returns the original operation/job. Same key + different text/service/version/public scope, or supplied versus omitted request, refuses with `idempotency_conflict`. A changed or malformed request never silently returns the prior operation or allocates another job. An unknown original outcome remains readback-only.

The wallet's payment approval already includes `termsHash` via `src/purchases.mjs#approvalBinding()` and the purchase commitment (`src/purchases.mjs#purchaseCommitment()`). Including request material in persisted terms makes those existing commitments cover it. Also bind it into any WS3/WS5 intent and seller session delegation before widening their authority. The native DEM transfer cannot carry this request; it does not gain purchase-specific attribution.

Spec: CORE §B.2 supplies canonical hashing; DACS-3 §8.5.1 supplies signed Agreement scope. **DACS defines no application purchase idempotency-key or portal-approval schema.** These are local durable-operation/consent obligations, not invented Standard fields.

### 3. Co-signed Agreement: bind exact request and digest

Use the existing DACS-3 field `terms.additionalTerms`. The supplied DACS-3 §8.5 explicitly declares this line in both `AgreementTerms` and `PayeeBoundAgreementTerms`:

```text
additionalTerms?: Record<string, unknown>
```

Proposed application entry (the namespaced key is application-defined):

```text
terms.additionalTerms["dacs-chatgpt-plugin:public-service-request:v1"] = {
  request: <the complete admitted PublicServiceRequest>,
  requestHash: <the recomputed 64-character lowercase digest>
}
```

Choose full request plus hash, not hash alone: the seller has the exact public input and a replaying buyer can reconstruct it from the Agreement without off-chain availability assumptions. Both parties re-admit it, recompute the digest and compare canonical bytes to the persisted buyer-approved request before creating any signing plan. The buyer checks the seller contribution, anchored Agreement and commitment against that same binding on every resume. A hash-only variant would require a separate exact-byte, content-addressed availability contract; none is specified here.

DACS-3 §8.5.1 says: “Each artifact follows the §B.2 canonical-form template, omitting the `signatures` field.” For the existing payee-bound artifact it specifies `"dacs-payee-bound-agreement:v1:" || agreement_hash`. The request entry therefore participates in the same hash and both signatures. CORE §B.7 SIG-5 requires preserving unknown members in the signed scope, although signature preservation alone does not require an older reader to enforce their meaning. The new application profile must enforce this entry before signing, paying or producing a request-based result.

**Do not overload `terms.deliverable.hash`.** DACS-3 §8.5.2 check 4 requires it to equal the hash of the Listing's complete anchored `offering.deliverable`; DACS-4 §9.3 defines that preimage as the `DeliverableSpec`, not the buyer request or eventual output.

Hook `src/dacs/purchase-protocol.mjs#planAgreementFromInput()` (derive/signing plan), `src/dacs/protocol-purchases.mjs#planRequest()` (bound context plan), `src/dacs/protocol-purchases.mjs#signRequest()` and `src/dacs/purchase-protocol.mjs#boundTermsMismatch()`. Context scope/exact input checks at `src/dacs/agreement-context-consumer.mjs#agreementContextScope()` and `src/dacs/dem-delivery-context-consumer.mjs#inputProblem()` must carry/check the same request. The demo provider at `src/devnet-demo/agreement-context.mjs#resolveBuyer()` currently produces request-free derive input. Seller proposal admission at `src/dacs/seller-agent.mjs#receiveProposal()` must independently derive the same draft rather than trust buyer/seller-provided arbitrary terms.

**SDK prerequisite:** `FixedPriceAgreementInput` in the installed `@kynesyslabs/dacs/dist/negotiate/fixedPrice.d.ts` has no additional-terms input. `@kynesyslabs/dacs/dist/negotiate/fixedPrice.js` constructs request-free terms. Current context validators allow exactly that derive shape; durable seller admission re-derives it. A reviewed SDK capability/version must carry the application extension consistently through derivation, seller reconstruction, signing and durable recovery. Do not append an entry after the SDK signing plan is made, edit vendor files, strip unknown terms, or bypass comparison. Until this support exists, request-based signing stays held.

Question for the Standard: “Does §8.4.1 step 1 (copying the posted Listing terms) permit per-job buyer requests in §8.5 `terms.additionalTerms`, when a signed Listing contract fixes their schema and bounds? Which conformance check must enforce that contract, including any auto-accept case?” DACS currently provides the extension field but no normative public-request semantics. This design does not add a new Standard field or activate auto-accept.

### 4. Deliverable and delivery evidence: name and verify the request hash

Proposal: a new, versioned application result schema includes `requestHash` (lowercase hex SHA-256) alongside existing `jobId`, `agreementHash`, Listing pin and report content. Require equality with the validated Agreement entry and persisted purchase terms. Generate the deterministic report solely from that Agreement request, not a later HTTP argument, operator-configured text or seller fixture. A request hash proves byte binding, not that the seller's analysis is correct; the deterministic service must also have reproducible result tests.

Hook the producer at `src/devnet-demo/deliverable.mjs#createDevnetPurchasedReportProducer()`, composition at `src/devnet-demo/composition.mjs#createDevnetDemoComposition()`, and seller's producer checks at `src/dacs/seller-agent.mjs#deliveryReport()`. A new version/kind avoids silently widening today's exact report shape at `src/devnet-demo/deliverable.mjs#isDevnetPurchasedReport()`. Coordinate matching artifact admission at `src/devnet-demo/artifact-anchor.mjs#artifactValid()`, `src/wallet/devnet-native-transport.mjs#signedTransaction()`, and `public/portal/embedded-wallet/sdk-provider.mjs#devnetDemoArtifactMatches()`; preserve wallet storage checks. Buyer readback at `src/dacs/purchase-protocol.mjs#verifyDelivery()`, `src/dacs/dem-delivery-consumer.mjs#readDemDeliveryReady()` and the native reader at `src/devnet-demo/native-delivery.mjs#createDevnetDemoDeliveryCapability()` must reject a missing/substituted request hash before rendering the result. Retain the signed-evidence checks at `src/dacs/delivery-evidence.mjs#isNativeDeliveryEvidence()` without adding a request field to that evidence shape.

Spec: DACS-4 §9.6.1 steps 2–5 require schema-conforming output, canonical payload hash and `SettlementEvidence.deliverableContentHash`. The evidence hashes the complete result including its application `requestHash`, linking evidence → result → request and Agreement. **There is no normative `requestHash` member for a storage-program result or delivery evidence in the Standard.** It belongs to the application payload schema identified by the signed Listing, and is transitively bound through existing evidence fields. No extra evidence field is needed.

### 5. Portal review: the same bytes before consent

Hook persisted views at `src/portal/routes.mjs#purchaseView()`, review rows at `public/portal/portal.js#termsRows()`, and the pre-signing plan comparison in `public/portal/portal.js#signAgreement()`, before `public/portal/portal.js#walletSign()`. Display service/version, the public-data label, entire input using text nodes with whitespace preserved, canonical byte count and full request hash. Provide the canonical JSON for inspection; never interpret input as HTML, Markdown instructions, a URL to fetch or code. Rendering must not initiate wallet or purchase actions.

Re-admit the persisted request and compare its canonical bytes/hash with the signed-plan draft and approved intent. Show the exact Agreement-derived request before signing, retain it on payment review and in the eventual result/receipt, and stop on any mismatch. Do not regenerate it from ChatGPT narration, summaries, browser locale, editable fields or current seller configuration. An edit requires a fresh purchase intent/key after resolving any original unknown operation.

Spec: DACS-3 §8.5.1 binds the bytes, and DACS-4 §9.6.1 provides public delivery. **The Standard has no portal review-screen specification.** These are application consent checks. Public-data declaration is not wallet approval and does not authorize a new artifact kind, fee, payment or retry.
