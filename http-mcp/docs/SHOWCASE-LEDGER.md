# Five-stage purchase ledger

Set `DACS_SHOWCASE_LEDGER=1` to display the read-only ledger in purchase portal views and the MCP status App (`ui://dacs/status-v6.html`). The switch defaults off; the existing status-v5 resource, tool schemas and rendered purchase output are retained when off.

Publication tools, signing routes and resources are retired in v2 regardless of the publication compatibility switch.

`loadConfig` refuses `DACS_SHOWCASE_LEDGER=1` together with `DACS_SHOWCASE_REPORT_VIEW=1` (`PURCHASED-REPORT-VIEW.md`): both change the purchase status App, and composing the two views is left to a later change. Each switch alone is accepted, and the deploy preflight reports the pair as `runtime-config-rejected`.

`src/mcp/showcase-progress.mjs` projects the recorded Listing checks, operation history, protocol view and payment observation. `public/portal/showcase-progress.mjs` renders the same projection on both surfaces. Neither module starts protocol work, polls, signs, sends or reads a chain. Existing explicit recheck actions retain their existing behavior.

- **Identify:** the Listing checks recorded at preparation. This is historical verification, not a fresh eligibility check. It is verified only when every named check the Listing verifier records (directory hash and coordinates, chain anchor presence, readback and owner, catalog freshness, Standard reader, purchase support) passed and the Listing id, version, content hash and anchor locator are bound; a partial or older check set stays pending, and any failed check is rejected.
- **Vet:** bound per-party composite references, where recorded, with the profile's stated Vet scope. Identity associations and bound references cannot establish an independent counterparty Vet pass. Missing verification and receipt proof remain visible; even operator composite closure does not establish complete mutual Vet.
- **Negotiate:** recorded two-party Agreement anchoring and independent commitment readback checks. A missing commitment explains the wait. Any unavailable transaction/block proof stays missing. A later fresh commitment gate refused with `commitment_unverified` makes Negotiate rejected and the earlier commitment pass historical; it is verified again only after a recorded recovery (a later verified commitment readback, or a payment handoff the fresh gate allowed). A later gate refused with `agreement_unverified` (fresh native Agreement readback) or `agreement_terms_mismatch` (committed terms) makes Negotiate rejected and the earlier Agreement pass historical; only a payment handoff the fresh gate allowed recovers it, because a commitment readback does not re-read the Agreement. Approval alone is not a recovery. After payment, a native evidence re-check reads the Agreement first; when that read does not verify (`agreement_unverified`, recorded as the event's `code`), Negotiate is rejected the same way until a later verified native evidence or native delivery read, or a payment handoff the fresh gate allowed.
- **Settle:** payment inclusion, job-bound payment evidence, Deliverable and delivery evidence appear separately. Inclusion says “included in block N”; it never supplies consensus finality. Report availability reaches `delivery-ready`. Pending or rejected delivery evidence retains its reason. Payment evidence is current only when the latest payment, native evidence or native delivery read verified it; after a later held or failed read, the retained proof is shown separately as historical.
- **Verify:** completion audit pending, even if fixture bundle references are recorded or the fixture protocol stage says `completed`. Rejected, held or unknown audit attempts remain visible. This ledger does not implement or establish native DACS-5 completion.

Every evidence row shows the recorded check, reason, transaction hash, block, artifact key/hash and observation scope. Unrecorded fields say “Missing proof”. The native consumer currently does not retain every upstream Vet/commitment receipt in the purchase view; the ledger does not fill those gaps by fetching or guessing. Every negative recorded attempt, including earlier failures of the same step and every repeated gate, handoff, readback, pointer and wallet refusal, remains inspectable in order with its reason, labelled current or historical; only the latest outcome sets the stage's current state. A refusal becomes historical only after a later recorded recovery for it or a later refusal of the same kind (for gate and handoff refusals, the same reason, since a different reason means a different check refused first). Unknown wallet outcomes are never labelled historical.

The listed history is bounded: each stage lists the latest 20 recorded protocol attempts and the latest 20 recorded refusals, each list preceded by one “Earlier recorded attempts” row when older ones exist. That row gives the number not listed, their history sequence range, how many are still current and how many are unknown outcomes; with any unknown outcome among them its state is `unknown`. Stage states are computed from the full history, and every attempt remains in the purchase history that `get_purchase_status` returns (`history`, by `seq`). Labelling uses one pass over the history.

Unknown payment outcomes remain readback-only. The switch changes presentation only and adds no broadcast retries or wallet authority. Manual ChatGPT host acceptance and browser layout checks remain separate from local node:test coverage.

Plugin v2 buys and discovers Listings. Listing publication is unavailable in this plugin; a separate seller kit is coming and has not been released.
